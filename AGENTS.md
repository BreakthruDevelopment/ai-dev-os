# AI Dev OS: rules for every agent

This repo is the operating system for the **30 apps in 30 days** build: who does what, how work moves, and the
rules every AI tool follows. Claude Code, Codex, Grok Build, Antigravity and Grok Bot all read this file.

The process is called the **BreakthruSoftwareFactory**. Its five gates (spec, build, review, release, close-out),
the definition of done and the required review are in [`FACTORY.md`](FACTORY.md); this file is its rulebook.

**New to the project?** Read [`BRIEFING.md`](BRIEFING.md) first: what we're building, every decision in force,
and what's been dropped.

## 1. Repo safety (non-negotiable)

The BreakthruDevelopment org holds other, unrelated applications that must never change.

- Touch only repos with the GitHub topic `30-apps-30-days`. Anything else is read-only.
- Before creating a repo, list existing names. If the name is taken, **stop and ask**; never reuse or rename.
- Never force-push, delete, rename, transfer or archive a repo or branch.
- Never push to `main`. Work on `<harness>/<task>` branches (`claude/…`, `codex/…`, `grok/…`, `antigravity/…`) and open a PR.
- Never commit or paste secrets. Keys go into GitHub Actions secrets or a cloud secret manager, entered by Michael.
- **Who merges.** Any harness may squash-merge an **app-repo** PR (a repo tagged `30-apps-30-days` other than
  `ai-dev-os` and `30-apps-infra`) only when every required check is green on the current head commit, including
  `Lint, test, build, smoke` and `Reviewer sign-off` (plus a Codex `Verdict: ready` review when the PR is labelled
  `security-sensitive`). Use `gh pr merge --squash --auto` to queue the merge when auto-merge is enabled on the
  repo, or `gh pr merge --squash` once the checks are already green. Never bypass branch protection, never use an
  admin merge, never merge your own red PR, and never merge with failing or pending checks.
- **Deploys and playbook changes: Claude Code merges** (Michael's standing instruction, 2026-11-12). Claude Code
  may also squash-merge PRs in `30-apps-infra` (deploys, `apps.yaml`) and in `ai-dev-os` (this playbook) once their
  required checks are green on the current head and, for `ai-dev-os`, a marked review is in; for an infra PR it
  first reads the plan and stops for Michael if it would destroy anything other than a known, explained change.
  Other harnesses never merge those two repos.
- **These stay with Michael:** **spec PRs** (gate 1, scope approval), entering secrets, and changing branch
  protection or rulesets. Michael can stop or reverse any merge or deploy; no agent changes branch protection.

## 2. Models, harnesses and agents

| Layer | What it is | Here |
| --- | --- | --- |
| **Model** | The LLM doing the thinking | Claude (Opus, Sonnet), OpenAI's Codex models, Grok, Gemini |
| **Harness** | The program that wraps a model so it can read files, run commands and open PRs; each has a subscription with its own usage limits | Claude Code, Codex, Grok Build, Antigravity, Grok Bot |
| **Agent** | A role (instructions, allowed tools, a goal) running inside a harness | The files in `roles/` |

One harness can run many agents, and any role can run in any harness that has capacity. Roles are defined once,
in `roles/`, as plain instructions. Claude Code gets them as subagents in `.claude/agents/`, generated by
`scripts/sync-claude-agents.py`; edit the role file, never the generated one.

| Harness | Subscription | Starts work when | Usually does |
| --- | --- | --- | --- |
| Claude Code | Claude | An issue is labelled `claude` (sessions, or scheduled tasks overnight) | Planner, reviewer, AI builder, deploys, template changes |
| Codex | ChatGPT Plus (tightest limits) | An issue is labelled `codex` | Fullstack on selected issues; second review on security-sensitive PRs |
| Grok Build | X (SuperGrok) | Michael runs `scripts/run-harness.sh grok` on his Mac | UI pages, fullstack issues, READMEs (used more from 2026-11-09) |
| Antigravity | Google AI Pro | Michael runs `scripts/run-harness.sh antigravity` on his Mac | Fullstack and docs (on trial) |
| Grok Bot | X (Grok) | Michael pastes in an issue, or an app's README and live URL | Backup builder when Grok Build is out of usage; launch posts and demo scripts (below) |

Grok Build and Antigravity are CLIs on Michael's Mac, not GitHub apps: labels don't trigger them, the runner
script does ([`runbooks/harnesses-on-mac.md`](runbooks/harnesses-on-mac.md)). Jules is gone: Google turns it
read-only after 2026-11-11 and shuts it down on 2026-12-31; Antigravity replaces it.

| Role (`roles/`) | Default harness | Can move to |
| --- | --- | --- |
| `planner` | Claude Code | — |
| `fullstack-builder` | Grok Build; Codex or Antigravity on the issues assigned to them; Claude Code for template changes | Claude Code, Codex, Antigravity, Grok Bot |
| `ai-builder` | Claude Code | Antigravity, Grok Build |
| `ui-builder` | Grok Build | Antigravity, Claude Code, Grok Bot |
| `reviewer` | Claude Code on every PR, plus Codex on security-sensitive PRs | — |
| `devops` | Claude Code | any (Terraform changes in `30-apps-infra`: Grok Build or Antigravity) |
| `docs-writer` | Grok Build | Antigravity, any |
| `ops-monitor` | Claude Code scheduled task (nightly, 5:37 AM Central, posts to the `Ops report (nightly)` issue in this repo) | Claude Code session |

**Grok Bot's jobs.** It holds no secrets and never merges. It has two jobs:

- **Backup builder.** When Grok Build is out of usage, Michael can paste a `grok`-labelled issue into Grok Bot,
  which then works it as the `ui-builder` or `fullstack-builder` named in the title: it reads that role file and
  the app repo's `AGENTS.md`, works on a `grok/<task>` branch and opens a PR. The PR goes through the same gates as
  any other (CI, the required `Reviewer sign-off`, Codex on `security-sensitive`); another harness merges it once
  green, per section 1. Michael doesn't also run `scripts/run-harness.sh grok` on an issue he has given Grok Bot.
- **Launch posts.** When an app goes live, Michael pastes its README and live URL into Grok Bot, which drafts an X
  post and a LinkedIn post (problem, what the app does, the AI feature, cloud, link, no invented numbers) and a
  two-minute demo script (the clicks in order and what each proves). Michael edits and posts them himself; Grok
  Bot never posts or opens accounts.

It no longer runs the ops monitor.

## 3. GitHub is the single source of truth

Harnesses never talk to each other directly. Work moves through:

| Thing | Where |
| --- | --- |
| What to build | `catalog.yaml` (this repo) and the app's spec at `specs/NN-slug.md` |
| The queue | One GitHub Project board across every app repo |
| Work items | Issues, each with a role in the title (`[ui-builder] Dashboard page`) and a harness label: `claude`, `codex`, `grok` or `antigravity` |
| Changes | Pull requests from `<harness>/<task>` branches |
| Status | PR checks, the board, and the Build Tracker (app 1) |
| What happened | A run log per app in `runs/NN-slug.md` |

**The harness label is the start signal.** Claude adds an issue's harness label only once the issues it depends
on are merged; until then its planned owner is in the spec. **Pick up only issues with your
harness's label**, and read the role file named in the title before starting. (`jules` labels may linger on old
repos; nobody picks them up.)
When a harness hits its usage limit, Michael (or the planner) relabels its open issues; nobody buys extra credits.

## 4. Daily flow (the BreakthruSoftwareFactory gates)

1. **Gate 1, spec. Planner** writes `specs/NN-slug.md` from `templates/spec.md`, opens one issue per slice with a role and a planned harness, marks security-sensitive slices, and adds them to the board. Michael approves the scope by merging the spec.
2. **Gate 2, build. Builders** open PRs against the app repo from `<harness>/<task>` branches. CI must be green: lint, typecheck, tests, build, smoke.
3. **Gate 3, review (required). Reviewer** (Claude Code) reviews every PR; Codex adds a second review on PRs labelled `security-sensitive`. Each posts a PR review ending in `Reviewer: claude-code` (or `codex`) and `Verdict: ready` or `Verdict: blocking`; the `Reviewer sign-off` check reads it. No merge without the reviewer check. Once CI and `Reviewer sign-off` are green on the current head, any harness may squash-merge the **app-repo** PR (see section 1).
4. **DevOps** adds the app to `apps.yaml` in `30-apps-infra` for the day's `live_cloud` (a PR Claude Code merges once green; AWS deploys itself within about 10 minutes), then runs the smoke test against the live URL. Migrations run when the app starts.
5. **Docs writer** fills in the README from `templates/app-readme.md`. Grok Bot drafts the launch posts and demo script from it.
6. **Claude Code** merges the `apps.yaml` PR once its checks are green and the plan holds no surprise; **Michael** posts the app. DNS records are created in Cloudflare by Terraform on deploy
   (`30-apps-infra` README, "Custom domains and DNS"); nobody adds them by hand.
7. **Overnight:** Codex and scheduled Claude Code tasks work queued issues into PRs; Grok Build and Antigravity work theirs whenever Michael starts the runner on his Mac. The ops monitor (a scheduled Claude Code task) posts to the `Ops report (nightly)` issue. Agents may squash-merge app-repo PRs that go green; Claude Code also merges green deploy and playbook PRs; spec PRs wait for Michael.

Steps 4 and 6 are **gate 4, release** (devops updates `apps.yaml`, Claude Code merges it, live smoke). **Gate 5,
close-out** is the run log in `runs/NN-slug.md`, the `catalog.yaml` status and `BRIEFING.md` "Where things stand",
and Grok Bot's launch drafts (Michael posts).

**Definition of done.** An app is done only with all four: a **filled README** (no template placeholder), a
**live smoke** pass after the latest deploy, a **run log**, and **`status: done`** in `catalog.yaml`. Details in
[`FACTORY.md`](FACTORY.md#definition-of-done).

## 5. Usage limits

All four subscriptions (Claude, ChatGPT Plus, X, Google AI Pro) have rolling limits; Codex's are the tightest, so
it gets only selected issues. Within Claude Code, roles run one after another, not in parallel.
Spread work by moving issues between harnesses, not by buying credits.
